# Синтетический мониторинг — Настройка

Настройка проверки доступности веб-систем описана отдельно — см. [Доступность веб-систем](/modules/infra/urlcheck.md). Ниже — настройка проверки сертификатов.

Порядок настройки: сначала проверка включается на коллекторе, затем в каждый наблюдаемый сетевой сегмент устанавливается чекер.

## Включение проверки сертификатов

Проверка сертификатов выключена по умолчанию. Кроме самого признака включения требуется общий токен, которым чекеры авторизуются при получении списка целей: ручка выдачи целей находится вне защищённого контура интерфейса, и токен — единственное, что её закрывает.

<!-- STEP_GUIDE:START Параметры включения проверки сертификатов на стороне коллектора: признак включения, общий токен авторизации чекеров и его назначение, поведение коллектора при включённой проверке и незаданном токене, что появляется в интерфейсе после включения. -->

Задайте переменные окружения коллектора:

| Переменная | Описание | По умолчанию |
|---|---|---|
| `SYNTHETICS_SSL_ENABLED` | Включить проверку сертификатов | `false` |
| `SYNTHETICS_AUTH_TOKEN` | Общий токен, которым все чекеры авторизуются при получении списка целей | — |

Токен один на весь парк чекеров: чекер называет себя именем, как APM-агент называет `app_name`, персональных секретов у чекеров нет. Значение произвольное — сгенерируйте случайную строку и укажите её же в конфигурации каждого чекера.

Если проверка включена, а токен не задан, **коллектор не запустится** и сообщит `SYNTHETICS_SSL_ENABLED требует SYNTHETICS_AUTH_TOKEN`. Это сделано намеренно: ошибку конфигурации видно сразу при старте, а не в виде отказов авторизации на каждом запросе чекера.

Пункт меню «Синтетический мониторинг → Сертификаты» присутствует всегда, независимо от признака включения. При включении коллектор создаёт хранилище целей и начинает обслуживать:

- добавление, изменение и удаление целей из интерфейса;
- выдачу назначенных целей чекерам.

Без включённого признака страница неработоспособна: хранилища целей не существует, поэтому вместо таблицы будет ошибка запроса, а сохранить цель не получится.

## Установка чекера

Чекер выполняет проверки и устанавливается в тот сетевой сегмент, где находятся проверяемые узлы. Он работает как интеграция инфраструктурного агента и обращается к коллектору только исходящими запросами, поэтому открывать доступ в сегмент снаружи не нужно.

<!-- STEP_GUIDE:START Установка чекера рядом с инфраструктурным агентом: доступные способы поставки, требования к среде исполнения, обязательные и необязательные параметры окружения с их назначением и значениями по умолчанию, порядок обновления, способ убедиться что чекер заработал. -->

Чекер — это скрипт на [Babashka](https://babashka.org), который запускает интеграция `nri-flex` инфраструктурного агента. Результаты уходят по той же шине, что и остальные инфраструктурные метрики, — отдельного канала записи у чекера нет.

### Требования

- Инфраструктурный агент GMONIT с интеграцией `nri-flex`.
- Исполняемый файл `bb` (Babashka) в `PATH` агента.
- Исходящий доступ с хоста агента до коллектора — по тому же адресу, куда ходят остальные агенты, — и до проверяемых узлов на их портах. Входящие подключения в сегмент не нужны.

### Параметры окружения чекера

| Переменная | Обязательна | По умолчанию | Описание |
|---|---|---|---|
| `COLLECTOR_URL` | да | — | Базовый адрес коллектора, например `https://collector.example.ru` |
| `CHECKER_NAME` | да | — | Имя этого чекера, например `dc-segment-a`. На него в интерфейсе назначаются цели |
| `SYNTHETICS_AUTH_TOKEN` | да | — | Токен из настройки коллектора выше, одинаковый для всех чекеров |
| `TIMEOUT_MS` | нет | `5000` | Таймаут по умолчанию, если у цели не задан свой |
| `BATCH` | нет | `50` | Сколько целей проверять одновременно |

Остальные параметры проверки (порт, протокол, SNI, STARTTLS, список адресов, таймаут, признак игнорирования невалидной цепочки) приходят от коллектора и задаются на цели в интерфейсе — в окружении их дублировать не нужно.

### Установка в виде Docker-образа

Чекер поставляется каталогом `synthetics-checker`: в нём `Dockerfile`, сам скрипт и конфигурация интеграции. Собранный образ — это штатный образ инфраструктурного агента с добавленным `bb` и чекером, поэтому его можно использовать как образ агента в том сегменте, где стоят проверяемые узлы.

1. Соберите образ:

```bash
cd synthetics-checker && docker build -t gmonit-ssl-checker .
```

2. Создайте `compose.yaml`:

```yaml
services:
  ssl-checker:
    image: cr.yandex/gmonit.ru/nri-cert-checker:main
    restart: unless-stopped
    environment:
      COLLECTOR_URL: https://collector.example.ru
      CHECKER_NAME: dc-segment-a
      SYNTHETICS_AUTH_TOKEN: <токен из настройки коллектора>

      # инфраструктурный агент → тот же коллектор, только пересылка
      NRIA_LICENSE_KEY: <лицензионный ключ GMONIT>
      NRIA_IS_FORWARD_ONLY: 'true'
      NRIA_DISPLAY_NAME: ssl-checker-dc-segment-a
      NRIA_COLLECTOR_URL: https://collector.example.ru/infra2/infra-api
      NRIA_COMMAND_CHANNEL_URL: https://collector.example.ru/infra2/command-api
      NRIA_IDENTITY_URL: https://collector.example.ru/infra2/identity-api

      # без этого параметры чекера не дойдут до интеграции
      NRIA_PASSTHROUGH_ENVIRONMENT: COLLECTOR_URL,CHECKER_NAME,SYNTHETICS_AUTH_TOKEN
```

`NRIA_IS_FORWARD_ONLY: 'true'` отключает сбор метрик самого хоста — чекер не должен выглядеть как ещё один наблюдаемый сервер. `NRIA_PASSTHROUGH_ENVIRONMENT` обязателен: без него агент не передаёт переменные в интеграцию и чекер не узнает ни адрес коллектора, ни своё имя.

3. Запустите:

```bash
docker compose up -d
```

### Установка в существующий агент

Если инфраструктурный агент в сегменте уже стоит, чекер можно добавить к нему:

1. Установите `bb` на хост агента.
2. Положите `ssl_checks.clj` из каталога поставки в `/opt/gmonit-ssl-checker/`.
3. Скопируйте `nri-flex/gmonit-ssl-checks.yml` в каталог `integrations.d/` агента.
4. Задайте `COLLECTOR_URL`, `CHECKER_NAME` и `SYNTHETICS_AUTH_TOKEN` — в блоке `env:` этого файла, через `passthrough_environment` в `newrelic-infra.yml` или в окружении контейнера.
5. Перезапустите агент.

### Обновление

- Docker: пересоберите или скачайте новый образ и перезапустите контейнер.
- Ручная установка: замените `ssl_checks.clj` и перезапустите агент.

Состояния на чекере нет — цели, их назначение и результаты хранятся в коллекторе, поэтому обновление и перезапуск ничего не теряют.

### Проверка

Откройте «Синтетический мониторинг → Сертификаты». Чекер появится в блоке «Чекеры» со статусом «работает» и временем последнего ответа — после первого запуска интеграции (по умолчанию в течение часа). Отчёт приходит даже если на чекер ещё не назначено ни одной цели, поэтому ждать назначения не нужно.

Проверить чекер, не дожидаясь коллектора, можно локально, передав цель прямо в окружении:

```bash
TARGETS_JSON='{"targets":[{"id":"t1","domain":"example.com","port":443}]}' \
  docker run --rm --entrypoint bb -e TARGETS_JSON \
  gmonit-ssl-checker /opt/gmonit-ssl-checker/ssl_checks.clj
```

## Имя чекера и наблюдение из нескольких сегментов

Каждый чекер называет себя сам, и цели в интерфейсе назначаются на это имя. Отдельная регистрация не нужна: чекер появляется в списке после первого отчёта, а до этого его имя можно ввести в форме цели вручную.

<!-- STEP_GUIDE:START Именование чекеров и схема наблюдения из нескольких сетевых сегментов: как имя связывает чекер с назначенными ему целями, что происходит при смене имени, размещение нескольких независимых чекеров, в том числе на одном хосте. -->

Имя из `CHECKER_NAME` — единственная связь чекера с его работой. На каждом запуске чекер запрашивает у коллектора цели, назначенные этому имени, и проверяет только их. Всё, что он отправляет, помечено этим же именем — по нему результат попадает в нужную строку таблицы и в нужную строку блока «Чекеры».

Выбирайте имя по сегменту или площадке, а не по хосту: `dc-msk`, `dmz`, `office-spb`. Имя видно пользователям в фильтрах и в таблице.

### Смена имени

Переименование чекера — это заведение нового чекера:

1. Новое имя не получит целей, пока их не переназначат в интерфейсе.
2. Старое имя останется в списке, пока на него назначены цели или пока в последних 48 часах есть его отчёты.

Поэтому меняйте имя вместе с переназначением целей, иначе проверки на время остановятся.

### Несколько сегментов

Схема одна: в каждом сегменте — свой чекер со своим именем. Один и тот же узел можно назначить нескольким чекерам и сравнить, что видно из разных сегментов.

Два чекера на одном хосте тоже возможны: один чекер — это один файл конфигурации интеграции в `integrations.d/` со своим `CHECKER_NAME`. Два файла с разными именами дают два независимых списка целей. Задавайте переменные в блоке `env:` каждого файла, чтобы имена не пересекались.

## Интервал проверки

Интервал задаётся в конфигурации интеграции и по умолчанию составляет один час: срок действия сертификата меняется медленно, чаще проверять незачем. Интерфейс фактический интервал не знает и исходит из значения по умолчанию, поэтому его изменение влияет на индикаторы состояния.

<!-- STEP_GUIDE:START Интервал выполнения проверок: где задаётся, значение по умолчанию и его обоснование, влияние изменения интервала на признак работоспособности чекера и на отображение целей при коротком выбранном диапазоне времени. -->

Интервал задаётся полем `interval` в файле конфигурации интеграции (`gmonit-ssl-checks.yml` в каталоге `integrations.d/` агента):

```yaml
integrations:
  - name: nri-flex
    interval: 1h
```

За один запуск чекер проверяет все назначенные ему цели. Расписания на отдельную цель нет. Значение по умолчанию — `1h`: срок действия сертификата меняется медленно, чаще проверять незачем.

Интерфейс фактический интервал не знает и всегда исходит из одного часа. Поэтому изменение интервала влияет на два индикатора:

- **Статус чекера.** Чекер считается работающим, если отчитывался в последние два часа (два интервала по умолчанию). Если поставить интервал больше часа, чекер будет помечен как «не отвечает» в промежутках между отчётами. Если меньше — он будет считаться работающим дольше, чем следует после фактической остановки.
- **Статусы целей.** Результаты берутся за выбранный в интерфейсе период. Если период короче интервала проверки, отчётов в него не попадёт и цели покажутся как «Нет данных» — страница выводит подсказку об этом. При интервале меньше часа таких подсказок не будет.

Уменьшать интервал имеет смысл только на время отладки: результат от этого точнее не станет, а нагрузка на проверяемые узлы вырастет пропорционально.
