# Коробочные оповещения — Настройка

## Включение пакета оповещений и интервал оценки

По умолчанию коробочный пакет оповещений **стоит на паузе**: после установки ни одно правило не срабатывает, пока пакет не включат явно. Интервал оценки правил по умолчанию равен **1 минуте**.

Поведение пакета задают две переменные окружения Grafana:

| Переменная | Описание | По умолчанию |
|---|---|---|
| `GMONIT_GRAFANA_DEFAULT_ALERT_PACK_ENABLED` | Включает пакет. При значении `true` все правила пакета снимаются с паузы. Любое другое значение или отсутствие переменной оставляет пакет на паузе | `false` (на паузе) |
| `GMONIT_GRAFANA_DEFAULT_ALERT_PACK_INTERVAL` | Переопределяет интервал оценки всех правил пакета | `1m` |

### Как правильно задать интервал

Значение `GMONIT_GRAFANA_DEFAULT_ALERT_PACK_INTERVAL` подставляется в правила как есть, поэтому указывайте его в формате длительности Grafana (например `30s`, `1m`, `2m`).

Требования к значению:

- **Кратно базовому интервалу планировщика (10 секунд).** Значения вроде `25s` или `1m5s` некорректны. Допустимы `10s`, `30s`, `1m`, `90s`, `2m` и так далее.
- **Не равно нулю.** Пустое или нулевое значение тоже некорректно.

Если значение указано некорректно, Grafana **не запустится**: провижининг правил пакета упадёт на старте. Поэтому после изменения интервала проверьте, что контейнер Grafana поднялся.

Чем меньше интервал, тем быстрее обнаруживаются нарушения и точнее сроки эскалации, но выше нагрузка на оценку правил. Для большинства установок значение по умолчанию `1m` оптимально; уменьшать его стоит только ради более быстрой реакции и при запасе по ресурсам.

Пример включения пакета с оценкой раз в 30 секунд:

```yaml
environment:
  GMONIT_GRAFANA_DEFAULT_ALERT_PACK_ENABLED: "true"
  GMONIT_GRAFANA_DEFAULT_ALERT_PACK_INTERVAL: 30s
```

## Подавление ложных оповещений «нет данных» при недоступности Collector

<!-- STEP_GUIDE:START Самомониторинг Collector как условие срабатывания правил «нет данных от агента»: зачем нужно (защита от ложного шторма оповещений, когда недоступен сам Collector), как это меняет поведение правил, параметры настройки — имя приложения Collector и включение подавления — и значения по умолчанию, включая предупреждение о взаимодействии этих параметров с отключённым самомониторингом. -->

В пакете есть правила «нет данных от агента» для APM, баз данных, хостов, контейнеров и хранилищ (см. [Состав пакета](/modules/alert-pack/guide.md#Состав-коробочного-пакета)). Они срабатывают, когда сущность перестаёт присылать метрики.

Особый случай — недоступность **самого Collector**: тогда метрики разом перестают поступать от всех агентов. Без защиты в этот момент сработали бы сразу все правила «нет данных» — ложный шторм оповещений, хотя сами приложения и хосты могут быть в порядке.

Чтобы этого не происходило, пакет использует самомониторинг Collector как признак «живого» приёма данных. Collector отправляет собственные метрики как отдельное приложение. Пока они поступают, отсутствие данных от агента трактуется как падение агента и правило срабатывает. Как только замолкает сам Collector, правила «нет данных» по отдельным сущностям за этот период **не срабатывают**: вместо шторма остаётся одно оповещение — о недоступности Collector.

Поведение задают две переменные окружения Grafana:

| Переменная | Описание | По умолчанию |
|---|---|---|
| `GMONIT_COLLECTOR_SELF_MONITORING_ENABLED` | Включает подавление правил «нет данных», пока Collector не присылает собственные метрики | `true` |
| `GMONIT_COLLECTOR_APP_NAME` | Имя приложения, под которым Collector мониторит сам себя | `[GMonit] Collector` |

**Когда менять `GMONIT_COLLECTOR_APP_NAME`.** Только если вы переименовали приложение самомониторинга Collector. Значение должно **точно** совпадать с этим именем — иначе пакет не распознает метрики Collector и подавление работать не будет.

**Когда выключать подавление.** Только если самомониторинг Collector отключён. Если оставить подавление включённым при отключённом самомониторинге, пакет никогда не увидит метрик Collector, посчитает приём данных постоянно «мёртвым» — и правила «нет данных» **замолчат навсегда**. В такой конфигурации выставьте `GMONIT_COLLECTOR_SELF_MONITORING_ENABLED: "false"`: правила будут срабатывать напрямую, без защиты от шторма.

Переменные применяются при старте контейнера Grafana, как и остальные параметры пакета.

## Маршрутизация уведомлений по уровням эскалации RACI

Эскалация по матрице RACI работает только для правил из коробочного пакета. Каждому уровню эскалации соответствует метка на оповещении, и доставку оповещений нужным командам вы настраиваете маршрутизацией по этим меткам.

<!-- STEP_GUIDE:START Маршрутизация оповещений по уровням эскалации: какие метки несут уровень эскалации, предварительное создание точек контакта, доступные способы настройки маршрутов, ручная настройка через политики уведомлений Grafana как альтернатива для сложных деревьев. -->

Каждое сработавшее оповещение пакета несёт две метки:

| Метка | Значения | Что означает |
|---|---|---|
| `gmonit_raci.level` | `L1`, `L2`, `L3` | Текущий уровень эскалации. `L1` присваивается сразу, `L2` и `L3` позже, пока нарушение держится |
| `gmonit_raci.severity` | `P1`, `P2`, `P3` | Профиль важности оповещения, задаёт скорость эскалации |

Одно нарушение порождает отдельное оповещение на каждый активный уровень. Так разные уровни можно направить разным получателям: `L1` дежурной команде, `L2` старшему дежурному, `L3` руководству.

Независимо от способа настройки, получателей (contact points) нужно создать заранее в разделе оповещений Grafana — например отдельные каналы для дежурной команды, старшего дежурного и руководства.

### Настройка через интерфейс GMONIT

Маршрутизацию по уровням эскалации можно настроить прямо в GMONIT, не открывая дерево политик Grafana вручную: правила задаются на странице **Оповещения → Маршрутизация**. Она управляет только ветками дерева уведомлений с метками `gmonit_*` — остальные ветки не затрагиваются.

Пошаговое создание правила — в разделе [Направить уровни эскалации разным получателям](/modules/alert-pack/guide.md#Направить-уровни-эскалации-разным-получателям).

Если дерево подготовлено через конфигурацию (provisioning), редактирование через интерфейс недоступно — ни через GMONIT, ни через нативный интерфейс Grafana; менять маршрутизацию можно только в источнике конфигурации.

### Ручная настройка через политики Grafana

Для сложных деревьев маршрутизации доступен полный контроль через стандартные политики уведомлений Grafana:

1. Откройте раздел оповещений Grafana → **Notification policies**.

2. Добавьте вложенную политику с условием по метке `gmonit_raci.level`:
   - `gmonit_raci.level = L1` → точка контакта дежурной команды
   - `gmonit_raci.level = L2` → точка контакта старшего дежурного
   - `gmonit_raci.level = L3` → точка контакта руководства

3. При необходимости уточните маршрут по метке `gmonit_raci.severity`, например чтобы критические оповещения (`P1`) шли по более срочному каналу.

## Срок подтверждения оповещений

Подтверждение останавливает эскалацию оповещения на текущем уровне, но не навсегда: у него есть срок, по истечении которого эскалация продолжается. Дежурный задаёт срок сам, а установка ограничивает диапазон.

<!-- STEP_GUIDE:START Параметры срока подтверждения оповещений: значение по умолчанию и верхняя граница, как они применяются к вводу пользователя и к подтверждениям от AI-агента, поведение по истечении срока. -->

Диапазон задают две переменные окружения коллектора:

| Переменная | Описание | По умолчанию |
|---|---|---|
| `ACK_TTL_MINUTE` | Срок подтверждения в минутах, предзаполненный в форме | `120` (2 часа) |
| `ACK_TTL_MAX_MINUTE` | Максимальный срок подтверждения в минутах | `2880` (48 часов) |

Как применяются значения:

- В форме подтверждения поле срока предзаполнено значением `ACK_TTL_MINUTE`; дежурный может задать любое значение от 1 минуты до `ACK_TTL_MAX_MINUTE`.
- Значение вне диапазона приводится к границе — как из интерфейса, так и при подтверждении [через AI-агента](/modules/mcp/guide.md#Пороги-подтверждения-и-цели-уровня-сервиса). Запрос на срок больше максимума не отклоняется, а урезается до `ACK_TTL_MAX_MINUTE`.
- По истечении срока подтверждение снимается автоматически. Если нарушение всё ещё держится, эскалация продолжается с того уровня, на котором была остановлена, а запись уходит в журнал со статусом `истекло`.

Верхнюю границу стоит соотносить с дежурной сменой: срок дольше смены означает, что нарушение может остаться без эскалации после того, как подтвердивший её инженер уйдёт с дежурства.

## Ограничение переопределений по командам

По умолчанию переопределения оповещений видны и доступны всем пользователям. Режим ограничения замыкает их на команды Grafana: пользователь видит и меняет только переопределения своей команды.

<!-- STEP_GUIDE:START Ограничение доступа к переопределениям оповещений по командам Grafana: включение режима, что требуется от Grafana для передачи проверяемой личности пользователя, как принадлежность к командам определяет доступные переопределения, поведение по умолчанию при выключенном режиме. -->

Режим включается переменной окружения коллектора:

| Переменная | Описание | По умолчанию |
|---|---|---|
| `TEAMS_RESTRICT_ENABLED` | Включить ограничение переопределений по командам Grafana | `false` |

При выключенном режиме (по умолчанию) переопределения видны и доступны на редактирование всем пользователям.

**Что требуется от Grafana.** Ничего дополнительно настраивать не нужно. Запросы к переопределениям проходят через встроенный plugin-proxy Grafana, который автоматически добавляет к ним подписанный идентификатор (ID-токен) текущего пользователя — по нему коллектор достоверно определяет, кто обращается и в каких командах Grafana он состоит. Достаточно, чтобы пользователь был авторизован в Grafana.

**Как права выводятся из команд.** У ряда заказчиков всем пользователям Grafana назначена роль Viewer, поэтому доступ разграничивается не ролью, а **членством в командах Grafana по соглашению об именах**:

| Команда пользователя | Доступ к переопределениям |
|---|---|
| `<Команда>` | просмотр правил этой команды |
| `<Команда>-editor` | просмотр и редактирование правил этой команды |
| `Global` | просмотр всех правил |
| `Global-editor` | просмотр и редактирование всех правил |

Пользователь с настоящей ролью Grafana **Admin** получает полный доступ независимо от команд.

Маркеры соглашения настраиваются переменными окружения:

| Переменная | Описание | По умолчанию |
|---|---|---|
| `TEAMS_RESTRICT_GLOBAL_NAME` | Имя команды с доступом ко всем переопределениям | `Global` |
| `TEAMS_RESTRICT_EDITOR_SUFFIX` | Суффикс в имени команды, дающий право на редактирование | `-editor` |
| `TEAMS_RESTRICT_PREFIX` | Префикс, ограничивающий, какие команды участвуют в разграничении. Пустой — участвуют все | (пусто) |

**Что видит пользователь.** В списке переопределений отображаются только правила его команд (или все — при доступе `Global`). При сохранении правило привязывается к командам, на которые у пользователя есть право редактирования; изменить чужое правило или затронуть команду без прав нельзя.
