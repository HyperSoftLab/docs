# Бизнес-мониторинг — Настройка

## Включение модуля

Модуль включён по умолчанию. Коллектору дополнительно нужен доступ к Grafana API: описания бизнес-систем и процессов хранятся на служебном дашборде, и коллектор читает их оттуда при каждом запросе.

<!-- STEP_GUIDE:START Включение модуля и доступ коллектора к конфигурации: параметры, их назначение, порядок получения токена, признаки того, что доступ не настроен. -->

Переменные окружения коллектора:

| Переменная | Описание | По умолчанию |
|---|---|---|
| `BUSINESS_MONITORING_ENABLED` | Включить модуль | `true` |
| `GRAFANA_API_URL` | URL к Grafana API, например `http://grafana:3000/api` | — |
| `GRAFANA_API_AUTHORIZATION` | Заголовок авторизации, например `Bearer glsa_xxxxxxxxxxxx` | — |

Две последние переменные общие с модулем инцидентов — если он уже настроен, отдельно для бизнес-мониторинга ничего делать не нужно.

Для получения `GRAFANA_API_AUTHORIZATION`:

1. Откройте Grafana → Administration → Service accounts
2. Создайте сервисный аккаунт с ролью **Editor**
3. Сгенерируйте токен
4. Укажите значение в формате `Bearer <токен>`

Роль Editor, а не Viewer, нужна потому, что через эти же переменные конфигурация не только читается, но и изменяется — при работе через MCP.

### Где хранится конфигурация

Описания бизнес-систем и процессов лежат не в базе данных, а на служебном дашборде Grafana **BM Configs** (uid `gmonit-bm-configs`) в папке **GMONIT**. Готовить его вручную не нужно: дашборд и папка создаются при первом открытии раздела, и вместе с ними заводится встроенная бизнес-система **«NR RUM APM user interactions»** — прохождение пользовательской сессии от браузера до серверных сервисов через распределённую трассировку. Её можно использовать как есть или как образец для собственной.

Права на запись этого дашборда решают, кто может менять конфигурацию. Пользователь без прав на запись видит бизнес-мониторинг в режиме только для чтения — страницы и панели работают, кнопки сохранения нет.

### Если доступ не настроен

Панели бизнес-мониторинга перестают работать целиком: коллектор не может развернуть идентификатор процесса в его описание и возвращает ошибку, в тексте которой названы обе переменные. В интерфейсе это выглядит как **«Bad request»** на панели — сам текст ошибки датасорс не показывает.

## Описание бизнес-системы

Бизнес-система отвечает на вопрос «откуда брать события и как понять, что они относятся к одному экземпляру». Настраивается один раз и переиспользуется всеми процессами внутри неё.

<!-- STEP_GUIDE:START Описание бизнес-системы: структура конфигурации, источники событий, идентификаторы экземпляра и их связывание между источниками, перечень сервисов. Создание, редактирование и удаление в интерфейсе. Скриншоты. -->

### Где настраивается

1. В боковом меню GMONIT нажмите **Бизнес-мониторинг** — откроется список бизнес-систем
2. **«Добавить бизнес-систему»** — создать новую, значок карандаша в строке — изменить, значок корзины — удалить
3. Форма состоит из двух полей: **«Имя бизнес-системы»** и **«Конфигурация (YAML)»**

<!-- ![Список бизнес-систем](./screenshots/bm_systems_list.png) -->

Удаление бизнес-системы удаляет и все её бизнес-процессы.

### Структура конфигурации

| Ключ | Назначение |
|---|---|
| `name` | Имя системы, оно же отображается в списке |
| `root_instance_id` | Идентификатор, по которому события собираются в один экземпляр. Все источники должны уметь его отдать — сами или через связку |
| `tables` | Где в каждой таблице лежат время, аккаунт и сервис |
| `providers` | Источники событий: что читать и как превратить строку в событие процесса |
| `entities` | Типы сервисов и запрос их состояния — для панели «Здоровье сервисов» |

### Таблицы

Описываются один раз и используются всеми источниками, которые из них читают:

```yaml
tables:
  browser_default_events:
    time_column: timestamp
    account_column: account_id
    entity_column: app_name_or_id
  traces_v2:
    time_column: timestamp
    account_column: account_id
    entity_array_column: app_names
```

`entity_column` — если строка относится к одному сервису, `entity_array_column` — если к нескольким, как у распределённой трассировки.

### Источники событий

```yaml
providers:
  front:
    table: browser_default_events
    entity_types: [rum_app]
    filter: "$.type = 'interaction'"
    slots:
      url_path: "path(JSONExtractString($.json, 'targetGroupedUrl'))"
      action_label: "url_path"
      journey_label: "format('\"{}\"', url_path)"
      provider_name: "'front'"
    instance_ids:
      session: "CAST($.session_id AS String)"
```

| Ключ | Назначение                                                                                                     |
|---|----------------------------------------------------------------------------------------------------------------|
| `table` | Из какой таблицы читать                                                                                        |
| `entity_types` | К каким типам сущностей (приложений, сервисов) относятся события источника                                     |
| `filter` | Условие, отсекающее лишние строки на входе. Необязательный                                                     |
| `instance_ids` | Идентификаторы экземпляра, которые источник умеет отдать                                                       |
| `slots` | Именованные выражения: вычисляются один раз и дальше доступны по имени — и в других слотах, и в условиях шагов |
| `root_instance_id_via` | Связка для источника, который не знает корневой идентификатор                                                  |

Префикс `$.` означает колонку таблицы источника. Без него имя трактуется как ранее объявленный слот — поэтому `action_label: "url_path"` ссылается на слот выше.

Три слота имеют особый смысл:

| Слот | Где виден |
|---|---|
| `action_label` | Узел на карте переходов конструктора |
| `journey_label` | Строка события в хронологии экземпляра |
| `provider_name` | Источник события в той же хронологии |

Источник без слотов участвует только в связывании идентификаторов, но не даёт узлов на карте.

### Связывание источников

Браузерные события знают идентификатор сессии, серверные трассировки — только идентификатор трассы. Чтобы связать их, один источник объявляет оба идентификатора, а остальные ссылаются на него:

```yaml
  ajax_span:
    table: spans
    instance_ids:
      session: "$.intrinsics['session']"
      trace_id: "$.trace_id"

  back_traces:
    table: traces_v2
    instance_ids:
      trace_id: "$.trace_id"
    root_instance_id_via: [[trace_id, ajax_span]]
```

Читается как «корневой идентификатор для этого источника берётся по `trace_id` из источника `ajax_span`».

### Состояние сервисов

Каждый тип сервиса задаёт запрос, возвращающий именованные показатели и границы «хорошо/плохо», и раздел GMONIT, куда ведёт клик по сервису:

```yaml
entities:
  apm_app:
    module: apm
    page: web
    health_query: >-
      SELECT app_name as entity_name, ... as health
      FROM ...
```

Готовые описания для APM- и браузерных приложений есть во встроенной бизнес-системе — их проще скопировать, чем писать заново.

## Описание бизнес-процесса

Бизнес-процесс — последовательность шагов внутри бизнес-системы. Помимо самих шагов конфигурация задаёт пороги, по которым платформа отличает зависший экземпляр от идущего, и правила классификации причин остановки.

<!-- STEP_GUIDE:START Описание бизнес-процесса: шаги и условия их прохождения, общая длительность процесса, пороги зависания на уровне шага и процесса, правила классификации причин отвала, пороги длительности для тепловой карты. -->

Бизнес-процессы собираются в [конструкторе](/modules/business-monitoring/guide.md#Собрать-бизнес-процесс) — форма и карта переходов покрывают всё, что описано ниже. Этот раздел нужен, когда конфигурацию правят текстом: в конструкторе есть переключатель на текстовое представление, и то же самое доступно через MCP.

### Шаги

```yaml
name: Покупка товара
entities:
  front: [MyWebApp]
  back_tx_span: [BackendA, BackendB]
steps:
  - name: Добавление в корзину
    conditions:
      front: "url_path = '/cart'"
      back_traces: "has(tx_names, 'WebTransaction/Expressjs/POST//api/cart')"
  - name: Оформление заказа
    conditions:
      front: "url_path = '/checkout'"
```

| Ключ | Назначение |
|---|---|
| `name` | Имя процесса |
| `entities` | Приложения, события которых берутся у каждого источника |
| `steps[].name` | Имя шага — оно попадает в воронку и хронологию |
| `steps[].conditions` | Условие прохождения шага, отдельно на каждый источник |

Условие пишется на языке выражений ClickHouse и опирается на слоты источника — на то, что бизнес-система объявила в `slots`. Шаг считается пройденным, если событие подошло под условие **хотя бы одного** из перечисленных источников; источники, не упомянутые в `conditions`, этот шаг не засчитывают никогда.

Порядок шагов строгий: экземпляр, дошедший до третьего шага, считается прошедшим первые два.

> ⚠️ **Имена приложений в `entities` должны совпадать с реальными.** Одно неверное имя обнуляет весь процесс — без ошибки, просто пустыми панелями.

### Пороги зависания

Определяют, с какого момента экземпляр считается не идущим, а застрявшим — от этого зависят операционный контроль и классификация причин отвала.

| Ключ | Уровень | Назначение |
|---|---|---|
| `steps[].stuck_threshold` | шаг | Порог для конкретного шага |
| `default_stuck_threshold` | процесс | Порог для шагов, у которых свой не задан |
| `max_journey_duration` | процесс | Максимальная разумная длительность процесса целиком |

Порог для шага берётся по первому заданному значению в этом порядке; если не задано ничего — два часа.

`max_journey_duration` задаёт ещё и окно, в котором события связываются в один экземпляр: то, что произошло позже, к экземпляру уже не относится. Если не задано, окно равно выбранному на дашборде диапазону.

Длительности пишутся строкой: `30s`, `15m`, `2h`, `1d` и их сочетания — `1h30m`.

### Пороги длительности шага

Задают границы раскраски на тепловой карте вкладки «Время прохождения»: до `good` — зелёный, после `bad` — красный.

```yaml
default_duration_thresholds: [1m, 10m]
steps:
  - name: Оплата
    duration_thresholds: [30s, 5m]
```

Шаг без собственных порогов берёт `default_duration_thresholds`, а при их отсутствии — `[1m, 10m]`. Пара, где второе значение не больше первого, игнорируется.

### Правила классификации причин отвала

Определяют содержимое вкладки «Анализ незавершённых сессий». Без этого блока вкладка сообщает, что правила не настроены.

```yaml
failure_reasons:
  known_failure_events:
    - name: "СМС-сервис недоступен"
      conditions:
        back_errors: "$.ex_class = 'SmsServiceUnavailable'"
  uninteresting_blacklist:
    - name: "Просмотр страницы"
      conditions:
        front: "$.type = 'interaction'"
  last_step_attributes:
    - name: "decline_reason"
      expr:
        back_traces: "JSONExtractString($.attributes, 'decline_reason')"
```

| Блок | Назначение |
|---|---|
| `known_failure_events` | Явные сбои: событие подошло — причина названа именем правила |
| `uninteresting_blacklist` | Рутинные события, которые не должны попадать в причины. Первое событие **вне** этого списка после последнего пройденного шага становится вероятной причиной |
| `last_step_attributes` | Значения, извлекаемые из строки, которая удовлетворила последний пройденный шаг, — например код отказа платежа |

Условия в `known_failure_events` и `uninteresting_blacklist` пишутся как условия шага. В `last_step_attributes` вместо условия стоит выражение, возвращающее значение.

Приоритет источников при классификации — сверху вниз: атрибут последнего шага, известный сбой, вероятный сбой, зависание. Экземпляр, для которого ничего не сработало и порог зависания ещё не вышел, считается идущим и в разбивку причин не попадает.

## Переменные дашборда

Панели бизнес-мониторинга не хранят описание процесса — они ссылаются на него по идентификатору. Поэтому дашборду, на который скопированы такие панели, нужны две переменные. Без них панель покажет «Bad request».

<!-- STEP_GUIDE:START Переменные бизнес-системы и бизнес-процесса на собственном дашборде: назначение, порядок создания, ограничения выбора, вариант с фиксированным процессом. -->

Обе переменные создаются одинаково: Dashboard settings → Variables → New → тип **Query**, датасорс **Infinity**.

**`bs` — бизнес-система:**

| Поле | Значение |
|---|---|
| Type | **JSON** |
| Method | GET |
| URL | `/business-monitoring/configs` |
| Root selector | *(пусто)* |
| Columns | `name` → as `__text`, `id` → as `__value` (оба string) |

**`bp` — бизнес-процесс:** то же самое, но Root selector:

```
$[id="${bs}"].processes
```

Это выражение JSONata: из списка систем берётся выбранная и возвращаются её процессы.

Обе переменные — **одиночный выбор, без «All»**. Значение подставляется в тело запроса как есть, и `{a,b}` от мультиселекта сломает запрос.

> ⚠️ **Четыре поля, из-за которых переменная «работает», но врёт.** Редактор Infinity по умолчанию создаёт CSV-запрос с примером данных внутри. Если оставить эти умолчания и просто вписать URL, переменная молча вернёт `foo`, `bar`, `baz` — не ошибку, а правдоподобный список. Проверьте: `Type = JSON`, `Root selector` заполнен по таблице выше, `Body content type = application/json` (для POST), и **inline-данные удалены**.

**Если процесс на дашборде всегда один.** Переменные можно спрятать, оставив панели как есть. Самый чистый способ — объявить `bs` и `bp` типом **Constant** со значениями идентификаторов: Grafana скрывает constant-переменные, подстановка работает как обычно, а выбора у читателя нет. Подойдёт и любой другой тип с `Hide = Variable`.

## Страница экземпляра

В интерфейсе клик по строке таблицы экземпляров открывает панель сбоку. На собственном дашборде таких панелей нет, поэтому клик ведёт на отдельную страницу экземпляра. Она создаётся один раз на инсталляцию и обслуживает все скопированные таблицы.

<!-- STEP_GUIDE:START Страница экземпляра для собственных дашбордов: назначение, требования к адресу и заголовку, состав переменных и панелей, порядок создания, изменение адреса перехода. -->

Ссылка в таблицах уже настроена и ведёт на дашборд с uid **`gmonit-bm-instance`**. Создать его нужно вручную.

Почему отдельная страница, а не панели рядом на том же дашборде: обновление панели, которую читатель не видит — плохой сценарий, а «прокрутить к панели» в Grafana сделать нечем.

1. Создайте дашборд с **uid** `gmonit-bm-instance` и заголовком **`BM instance`**.

   Заголовок важен: Grafana делает из него slug (`BM instance` → `bm-instance`), и адрес получается точно такой, какой стоит в ссылке. Иначе Grafana будет каждый раз перенаправлять на канонический адрес.

   Задать uid в интерфейсе напрямую нельзя. Два способа:

   - **Экспорт → правка → импорт.** Соберите дашборд как обычно, Export → Save JSON, поправьте в файле `"uid"`, затем Dashboards → New → Import → вставьте JSON.
   - **Через API**, если под рукой токен:

     ```bash
     curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"dashboard":{"uid":"gmonit-bm-instance","title":"BM instance","panels":[],"schemaVersion":41},"overwrite":true}' https://<grafana>/api/dashboards/db
     ```

     Ответ содержит `"url": "/d/gmonit-bm-instance/bm-instance"` — это и есть адрес из ссылки.

2. Добавьте три переменные: **`instance_id`** (textbox), а также **`bs`** и **`bp`** — те же, что в разделе [Переменные дашборда](/modules/business-monitoring/setup.md#Переменные-дашборда). Ссылка передаёт все три в адресе.

3. Скопируйте на страницу панели «Сводка по экземпляру», «Шаги» и «Прохождение шагов» со вкладки «Обзор» — панель за панелью, как описано в разделе [Собрать собственный дашборд](/modules/business-monitoring/guide.md#Собрать-собственный-дашборд).

4. Сохраните.

Теперь клик по строке в любой скопированной таблице экземпляров — «Экземпляры», «Зависшие» на операционном контроле, таблица на разборе незавершённых сессий — открывает эту страницу для выбранного экземпляра.

Держите страницу в другом месте? Поменяйте адрес в **Panel → Data links → URL** у таблицы: это единственное поле, которое решает, куда ведёт клик.
