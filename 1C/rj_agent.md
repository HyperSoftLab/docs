# Установка агента для чтения Журнала регистрации 1С (Docker Compose)

Данный документ описывает процесс установки и настройки агента для чтения Журнала регистрации (ЖР) 1С с использованием Docker Compose. Агент построен на основе Infrastructure Agent + nri-flex + парсер ЖР (.NET) в составе образа `infrastructure-bundle:1c-master`.

**Целевая среда:** Linux-сервер с Docker и Docker Compose (отдельная ВМ для агентов 1С).

> **Рекомендация:** Наиболее эффективный способ — расшарить папку с ЖР на сервере 1С и смонтировать её (NFS/CIFS) на ВМ с агентами. Так агенты не нагружают серверы 1С.

> ⚠️ **ВАЖНЫЕ УСЛОВИЯ:**
> * Папка с Журналами регистрации (`reg_*`) должна быть доступна на сервере с агентом (NFS/CIFS/локально).
> * **Формат ЖР: `.lgp` + `.lgf`** (новый бинарный формат, по умолчанию с 1С 8.3.22).
> * **GMonit Collector** должен быть доступен по HTTPS (порт 443).
> * Docker и Docker Compose установлены.


## Установка и настройка

Вы получили архив `jr-agent-offline.tar.gz` с агентом чтения Журнала регистрации 1С.

**Целевая среда:** Linux-сервер с Docker и Docker Compose.

### 0\. Предварительные требования

* **Docker** и **Docker Compose** установлены.
* Папка с ЖР смонтирована на сервер (NFS/CIFS) или доступна локально.
* Сетевой доступ до коллектора GMonit по порту **443 (HTTPS)**:
    ```bash
    curl -sk https://<<COLLECTOR_HOST>>/health
    ```
    Должен вернуть `ok`.

### 1\. Распаковка архива

```bash
tar -xvzf jr-agent-offline.tar.gz
cd jr_agent_bundle/
```

### 2\. Загрузка Docker-образа

```bash
docker load -i infrastructure-bundle-1c.tar
```

**Проверка:**

```bash
docker images | grep infrastructure-bundle
```

### 3\. Настройка

**3а. Файл `.env`** — укажите путь до ЖР:

```bash
nano .env
```

| Плейсхолдер | Описание | Пример |
| --- | --- | --- |
| `<<REG_LOG_PATH>>` | Путь до директории с ЖР на хосте | `/mnt/erp/srvinfo-1540/reg_3541` |

**3б. Файл `appsettings.json`** — настройте параметры:

| Плейсхолдер | Описание | Пример |
| --- | --- | --- |
| `<<TIMEZONE>>` | Часовой пояс сервера 1С | `Europe/Moscow` |
| `<<SKIP_DATE>>` | Не читать события ранее этой даты | `2025-11-01T00:00:00` |

**3в. Файл `docker-compose.yml`** — замените плейсхолдеры:

| Плейсхолдер | Описание | Пример |
| --- | --- | --- |
| `<<CONTAINER_NAME>>` | Имя контейнера | `jr-agent-erp` |
| `<<COLLECTOR_HOST>>` | Полный хост коллектора GMonit | `collector.company.com` |
| `<<OVERRIDE_HOSTNAME>>` | Имя хоста в GMonit (отображается в UI) | `1CEventLog-ERP` |

> **Самоподписанные сертификаты:** раскомментируйте строки `NRIA_CA_BUNDLE_FILE` и volume `./ssl:/gmonit/ssl`, закомментируйте `NRIA_SELF_INSTRUMENTATION` и `NRIA_SELF_INSTRUMENTATION_APM_HOST`. Положите CA-сертификат в `./ssl/rootCA.crt`.

> **Важно:**
> * `NRIA_IS_FORWARD_ONLY: 'true'` — агент только отправляет данные, не принимает команды.
> * `NRIA_EVENT_QUEUE_DEPTH: 10000` — увеличенная очередь для больших объёмов ЖР.
> * `GM_RLA_MIN_AGE_S: 15` — минимальный возраст события для обработки (защита от чтения незавершённых записей).
> * `GM_RLA_SKIP_INCOMPLETE_RECORDS: true` — пропуск неполных записей (защита от ошибок парсинга).
> * `GM_RLA_SKIP_ON_PARSE_ERROR: true` — продолжать работу при ошибках парсинга (не останавливать агент).

### 4\. Создание директорий

```bash
mkdir -p agent_log state
```

### 5\. Запуск

```bash
docker compose up -d
```

### 5а\. Посев позиции чтения при первом запуске (важно для баз с историей)

> **Зачем.** При первом запуске на чистом `state/` экспортёр читает ЖР **с самого начала истории** и идёт по всем `.lgp`-файлам (месяцы данных), пока не дойдёт до актуальных. На базе с длинной историей (особенно по сети/CIFS) этот «холодный старт» не успевает за `command timeout` в `nri-flex` (`600000` мс) — процесс `EventLogExporter` убивают каждый цикл, состояние не сохраняется, и в коллектор уходят только **error-записи** (`context deadline exceeded` / `signal: killed`), реальных событий нет. Параметр `SkipEventsBeforeDate` фильтрует только то, что **отправляется**, но НЕ ограничивает **скан** истории — поэтому он не спасает.
>
> **Решение** — вручную задать стартовую позицию, чтобы агент начал с нужного файла, а не с начала истории.

**Шаги (для каждой ИБ с уже накопленной историей):**

1. Узнайте имя свежего файла журнала: в каталоге ЖР базы `…/reg_<порт>/<GUID-ИБ>/1Cv8Log/` возьмите `.lgp` недавней даты (формат `ГГГГММДД000000.lgp`, например вчерашний `20260610000000.lgp`).
2. Создайте указатель позиции `state/<GUID-ИБ>/eventlog_position.txt` из ДВУХ строк — имя `.lgp` и смещение `0`:

   **С хоста (проще):**
   ```bash
   mkdir -p state/<GUID-ИБ>
   printf '%s\n0\n' '20260610000000.lgp' > state/<GUID-ИБ>/eventlog_position.txt
   ```
   **Или изнутри контейнера:**
   ```bash
   docker compose exec infra-agent bash
   cd /var/lib/log-exporter && mkdir <GUID-ИБ> && cd <GUID-ИБ>
   vi eventlog_position.txt      # строка 1: 20260610000000.lgp   строка 2: 0
   ```
   (`/var/lib/log-exporter` внутри контейнера = каталог `state/` бандла.)
3. Перезапустите агент: `docker compose up -d` (или `docker compose restart infra-agent`).
4. Проверьте, что позиция двигается (агент «дочитывает» в реальном времени):
   ```bash
   cat state/<GUID-ИБ>/eventlog_position.txt   # смещение во 2-й строке растёт
   ```
   — события должны пойти в дашборд «Журнал регистрации» уже без поля `error`.

> Дату/файл в позиции выбирайте в пределах окна хранения данных (TTL коллектора, по умолчанию 30 дней) — более старые события всё равно удалятся при вставке.

### 6\. Проверка корректности работы

**Статус контейнера:**

```bash
docker compose ps
```

Ожидаемый результат: контейнер `running`.

**Логи агента:**

```bash
docker compose logs -f infra-agent --tail=50
```

**Проверка подключения к коллектору:**

```bash
docker compose logs infra-agent | grep -i "connected\|connect got id"
```

**Проверка чтения ЖР:**

```bash
docker compose logs infra-agent | grep -i "1CEventLog\|EventLogExporter"
```

Ожидаемый вывод — строки с обработанными событиями ЖР без ошибок.

**Проверка состояния (до куда прочитано):**

```bash
ls -la state/
```

Должны появиться файлы-указатели по каждой информационной базе.

### 7\. Критерии успеха

| Критерий | Как проверить |
| --- | --- |
| Контейнер запущен | `docker compose ps` → `running` |
| Агент подключён к коллектору | В логах: `application connected` |
| ЖР читается | В `state/` появились файлы состояния |
| Нет ошибок доступа к ЖР | Отсутствует `Permission denied` или `No such file` |
| Нет ошибок коллектора | Отсутствует `connection refused` |
| Данные в GMonit | UI → 1С → Журнал регистрации → события видны |

### 8\. Типичные ошибки и решения

| Ошибка | Причина | Решение |
| --- | --- | --- |
| `Permission denied` для `/var/cluster-reg-logs` | Нет прав на чтение ЖР | Проверьте права на смонтированную директорию. Volume монтируется как `:ro` |
| `No such file or directory` | Неверный путь в `.env` | Проверьте `REG_LOG_PATH` — директория должна содержать файлы `*.lgp` и `*.lgf` (новый формат). Файлы `1Cv8.lgd` (старый SQLite-формат) парсером не читаются |
| `connection refused` к коллектору | Нет сети до GMonit | Проверьте firewall: `curl -sk https://<<COLLECTOR_HOST>>/health` |
| `x509: certificate signed by unknown authority` | Самоподписанный сертификат | Настройте `NRIA_CA_BUNDLE_FILE` и volume `./ssl` |
| Пустой `state/` | Нет событий новее `SkipEventsBeforeDate` | Уменьшите дату в `appsettings.json`. Если при этом в коллектор идут только error-записи — это не про дату, см. строку ниже |
| Только error-записи в ЖР (`context deadline exceeded` / `signal: killed`, `error_exec:/log-exporter/EventLogExporter`); per-IB лог `processing…` каждые ~10 мин; реальных событий нет | «Холодный старт»: экспортёр сканирует всю историю ЖР с начала и не укладывается в `command timeout` (`600000` мс) → процесс убивают каждый цикл, состояние не сохраняется. `SkipEventsBeforeDate` фильтрует только эмит, не скан | Посеять стартовую позицию `eventlog_position.txt` — см. раздел «5а. Посев позиции чтения» |
| Контейнер перезапускается | Ошибка конфигурации | `docker compose logs infra-agent --tail=100` для диагностики |

### 9\. Управление агентом (справочник команд)

| Действие | Команда |

| Запуск | `docker compose up -d` |
| Остановка | `docker compose down` |
| Перезапуск | `docker compose restart infra-agent` |

### 11\. Мониторинг нескольких информационных баз

Агент автоматически обнаруживает все ИБ в директории ЖР (`reg_*`). Каждая ИБ получает свой указатель в директории `state/`. Для мониторинга ЖР разных серверов 1С — создайте отдельные экземпляры агента (отдельные `docker-compose.yml` с разными `.env` и `container_name`).

> **Очень большую/высоконагруженную ИБ** (несколько ГБ ЖР, тяжёлый поток) выносите на **отдельный экземпляр агента** — объём одной такой базы занимает поток обработки и тормозит остальные; мелкие базы можно держать на одном агенте. Для каждой ИБ с накопленной историей не забудьте **посеять позицию** (раздел 5а), иначе холодный старт упрётся в таймаут.
